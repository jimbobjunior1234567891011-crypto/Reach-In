# Reach-In v0.1.0 — smoke test, 2026-09-05

Run by driving the game from the terminal: `tools/run-client.ps1` launches an
isolated NeoForge client with only Reach-In loaded, `tools/mcctl.ps1` sends real
mouse and keyboard input and captures the window, `tools/smoke.ps1` sequences the
whole thing and saves a screenshot per step.

Environment: NeoForge 21.1.221, Minecraft 1.21.1, 1280x720 client, survival mode.
Run at GUI scale 3 (panel overlaps the GUI) and GUI scale 2 (panel sits beside it).
Both pass.

## Results

| # | Step | Result |
|---|------|--------|
| 1 | Hover a shulker in the inventory | Panel renders, correct title, vanilla styling |
| 2 | Pick up 64 diamonds, left-click into grid cell 0 | Moved into the shulker |
| 3 | Right-click a grid cell | Vanilla split behaviour |
| 4 | Close and reopen the inventory | Contents persisted |
| 5 | Shift-click a grid item | Went to the player's hotbar |
| 6 | Shift-click an inventory item | Went into the shulker |
| 7 | Escape | Closed the grid, left the screen open |
| 8 | `/data get entity @s SelectedItem` | `minecraft:container: [{item: {count: 64, id: "minecraft:redstone"}, slot: 0}]` |
| 9 | Open a chest with the grid available | Both render side by side |
| 10 | Hover the shulker inside the chest screen | Panel binds normally |
| 11 | Shift-click a chest item | Went to the player inventory, **not** the shulker |
| 12 | Shift-click a grid item from the chest screen | Went to the player inventory |

Step 8 is the one that matters most: it reads the real item back through vanilla's
own command, so the contents are genuinely on the `CONTAINER` component and not
just something the panel is drawing.

## Bugs found and fixed during the run

**The render hook did not exist.** `@Inject` targeting `Screen.render` inside
`AbstractContainerScreen.render` failed with "Scanned 0 target(s)" — NeoForge
patches that method so it never calls `super.render`, calling `renderBackground`
directly instead. Replaced both mixins with NeoForge's own
`ContainerScreenEvent.Render.Background` and `.Foreground`.

**The panel was see-through.** Items and the player preview render through a
deferred buffer source that batches by render type rather than draw order, and the
preview is drawn with depth testing. Fixed with `graphics.flush()` plus drawing the
whole panel at Z 200 — above the screen's own items, below vanilla's tooltip layer.

**Clicks landed on the wrong slot.** With the panel overlapping the GUI, a click on
grid cell 0 was applied to armour slot 6. Vanilla's `findSlot` returns the *first*
matching slot in menu order, and the grid cells are appended last, so a parent slot
always won. The trace made it obvious:

```
[reachin] clicked side=C slotId=6 type=PICKUP base=46 host=36 valid=true
```

Fixed by injecting into `findSlot` to check the cells first, and by resolving points
on the panel that are not on a cell to nothing so the panel is not a window into
whatever it covers.

**Shift-click out put items in the offhand.** `moveItemStackTo(stack, 0, base, true)`
searched everything before the grid, and in the player's own menu the last slot
before the grid is the offhand, which a reversed move reaches first. Now restricted
to slots backed by `Inventory` with a container index below 36 — the main inventory
and hotbar, excluding armour, crafting and offhand.

## Known limitation

At GUI scale 3 on a 720p window there is no room for a 178-wide panel beside a
176-wide GUI, so it overlays the parent screen centred, covering the crafting and
armour area. It is fully usable there — hit-testing prefers the grid — but scale 2
or a larger window is where it looks right.

## Not covered

Creative inventory (out of scope for v1). Multiplayer with a second player. Drag
distribution, double-click collect and hotbar number swap, which come from vanilla
for free but were not exercised here.
